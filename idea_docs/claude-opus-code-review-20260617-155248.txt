CODE REVIEW — okay-hermes-voice intent/router/voice runtime
Reviewer: Claude Opus (read-only) · Branch main @ 72c9fe8
================================================================

SUMMARY
The router architecture is sound and genuinely local-first-friendly: deterministic route selection (interaction_routes/choose.py) is decoupled from the LLM classifier, acks are cached audio with no per-call agent, and the heavy path reuses the warm in-process Hermes agent. But there are real conflicts with the stated product direction — most notably the default STT provider is NOT Parakeet, the "fast intent" path is a remote OpenRouter call (no BERT/local engine exists), and barge-in is absent. Details below.

----------------------------------------------------------------
AREA 1 — Router schema/config vs route ∈ {local, chat, tools, agent}
----------------------------------------------------------------

[A1-1] SEV: LOW (terminology/spec drift)
Evidence: interaction_types.py:20-26 — RouteTarget = {immediate_only, small_model, heavy_agent, ask_clarification, safety_flow}.
Impact: The implemented route set does not match the review brief's {local, chat, tools, agent}. This is a naming/spec mismatch, not a bug — the implemented taxonomy is arguably richer (it splits safety + clarification out). But "tools" is not a first-class route: tool-bearing requests are funneled into heavy_agent (choose.py:28-32). If the product spec truly wants a distinct "tools" lane (e.g. a fast structured tool-exec path separate from full agent), it does not exist.
Fix: Either (a) update the spec/docs to ratify the 5-target taxonomy as canonical, or (b) if a dedicated fast "tools" lane is intended, add a RouteTarget and a handler in answer.py. Don't leave the two vocabularies floating.
Test: Add tests/interaction_router/test_route_selection.py case asserting the full canonical RouteTarget set, so the taxonomy is pinned and drift is caught.

[A1-2] SEV: MEDIUM (config conflicts with local-first direction)
Evidence: daemon_config.py:71-77 and router_config.py:14-20 — interaction_router_provider/small_model_provider both default to "openrouter", model "google/gemini-2.5-flash-lite". Your USER profile explicitly says "avoid OpenRouter/gpt-5.5".
Impact: The "hyper-fast intent" path is a remote OpenRouter round-trip on every voice turn (router_call.py:25). This conflicts with both the stated "BERT-style local intent engine" direction and your recorded anti-OpenRouter preference. Every wake → request incurs cloud latency + sends the transcript off-box (see A5-1).
Fix: Make the default router provider a local/Nous-aligned endpoint, or introduce the local intent classifier (below) as the default with the LLM router as fallback. At minimum change the default away from openrouter.
Test: test_config.py assertion that default provider is the intended local-first value (guards regressions to openrouter).

[A1-3] SEV: MEDIUM (missing BERT-style local intent engine)
Evidence: No local-intent module exists — search for bert/embedding/sentence_transformer/onnx-intent returns only the wakeword ONNX (audio/wake/inference.py:5). The only "fast" classification is the remote LLM in interaction_clients/router_classification.py:9.
Impact: The core desired direction ("hyper-fast BERT-style intent engine for simple commands; cached near-instant common responses") is unimplemented. Today every non-close, non-disabled request waits on a network classifier before even the ack plays.
Fix: Add a local first-stage classifier (e.g. a small ONNX intent model or even a curated phrase→intent table) that resolves high-confidence simple commands without the LLM, falling through to the LLM router only on low local confidence. Mirror the wakeword ONNX loading pattern.
Test: New tests/interaction_router/test_local_intent.py: known command strings classify locally with no provider client call (assert resolve_provider_client is never invoked).

[A1-4] SEV: LOW (close-phrase sets diverge / partial dead code)
Evidence: interaction_routes/close_phrases.py:4-12 LOCAL_CLOSE_PHRASES = {close, close voice, close voice mode, stop listening, end voice mode, cancel, never mind}; daemon_config.py:123-129 conversation_close_phrases = {close, please close, close voice, close voice mode, close conversation, close hermes}. Runner checks is_close_transcript (daemon set) at runner.py:102 BEFORE routing, while choose.py:16 checks the router set.
Impact: Two non-identical close vocabularies. "stop listening"/"cancel"/"never mind" only close via the router path; "please close"/"close conversation"/"close hermes" only via the daemon path. Also the router set is matched with inline normalization (choose.py:15) that does NOT strip the "okay hermes " prefix that normalize_voice_command does (normalization.py:12), so "okay hermes cancel" behaves inconsistently between the two checks.
Fix: Single source of truth — have choose.py consume the same normalized close-phrase set as is_close_transcript (normalize_voice_command), or merge both lists into one constant used by both call sites.
Test: test asserting every phrase in conversation_close_phrases routes to IMMEDIATE_ONLY/close, and that "okay hermes <phrase>" normalizes identically in both paths.

AREA 2 — Latency bottlenecks
----------------------------------------------------------------

[A2-1] SEV: HIGH (default STT is not Parakeet — transcript-first path is off by default)
Evidence: daemon_config.py:89 stt_provider = "hermes". recording.py:90 only starts live Parakeet streaming when bool(cfg["parakeet_live_streaming"]) AND is_parakeet_provider(cfg["stt_provider"]). With the default "hermes" provider, is_parakeet_provider is False, so live streaming never starts and turn_input.py:90-97 always takes the post-recording transcribe_command batch path.
Impact: Directly contradicts product direction ("Keep Parakeet streaming transcription as the default transcript-first path"). Out of the box, users get batch STT after recording ends — adding full transcription latency to every turn and disabling the streamed-text endpointing (recording.py:152-159) that makes turn-end detection fast. parakeet_live_streaming=True (daemon_config.py:109) is a no-op given the default provider.
Fix: Default stt_provider to the Parakeet streaming provider (the value is_parakeet_provider recognizes), or gate live streaming on parakeet_live_streaming alone and have it select Parakeet. Verify is_parakeet_provider("parakeet_unified_streaming") path end-to-end.
Test: test_default_config asserting stt_provider default engages Parakeet; a record_command test with the default cfg asserting start_parakeet_live_streaming is invoked.

[A2-2] SEV: MEDIUM (ack cannot play until remote router returns)
Evidence: request_route.py:18-28 — plan_interaction_route() (which calls the remote classifier, planning.py:19) must complete before the ack template is known and play_interaction_ack fires. The ack is the thing that's supposed to feel "near-instant."
Impact: Perceived responsiveness is bounded by router network latency (timeout 1.5s, router_config.py:16). The user hears silence from end-of-speech until the classifier replies. The looping-ack mechanism (ack_playback.py:26-39) masks long heavy-agent time but not the pre-classification gap.
Fix: Play a provisional default ack (got_it) immediately on final transcript, then let routing refine/stop it — or resolve ack locally from the local intent engine (A1-3) before the LLM router runs. The deterministic GOT_IT default already exists (ack_default.py:10); hoist it ahead of classification.
Test: test asserting an ack is scheduled before classify_request returns (e.g. classifier blocked on an event, assert ack played first).

[A2-3] SEV: LOW (router timeout reused as small-model answer timeout)
Evidence: small_model_answer.py:26 passes timeout=cfg.router_timeout_seconds (default 1.5s) to the small-model completion. The small model GENERATES up to 300 tokens (line 25).
Impact: A 1.5s timeout for a 300-token generation will almost always trip, silently returning None (line 30/41) and falling back to heavy Hermes (answer.py:34). The small-model fast path is effectively dead whenever it's enabled. Misclassified as a latency win; it's a latency+cost loss (one wasted call then the full agent).
Fix: Add a separate small_model_timeout_seconds (generous, e.g. 8–12s) distinct from the classifier timeout.
Test: test_client_classification-style test asserting the small-model call receives a timeout > router_timeout_seconds.

AREA 3 — Cancellation, stale-turn, barge-in, queued background results
----------------------------------------------------------------

[A3-1] SEV: HIGH (no voice barge-in anywhere)
Evidence: The only cancellation source is the visualization popup file flag — services.is_visualization_cancel_requested → visualization/state/cancel.py:10, consumed by ActivationCancellation.requested (cancellation.py:23). No audio/VAD path interrupts playback or recording on the user speaking. play_tts_file/_wait_playback_process (wait_process.py:21-30) only poll the popup cancel flag and STOP.
Impact: Conflicts with the "smart assistant" feel — the user cannot interrupt a long spoken answer by talking; they must use the popup (which is optional). During TTS playback the mic isn't being evaluated for wake/interrupt at all. This is the single biggest UX gap for the stated direction.
Fix: Add an optional VAD/wakeword-during-playback barge-in that sets the cancel signal feeding _playback_cancel_requested. The wakeword ONNX is already loaded; reuse it as an interrupt detector during speak_response.
Test: Simulated barge-in test: a cancel_check that flips True mid-playback causes _wait_playback_process to terminate and return cancelled=True (this primitive is already covered — extend it to an end-to-end speak_response barge case).

[A3-2] SEV: MEDIUM (stale-activation guard only covers cooldown window, not in-flight sessions)
Evidence: native_activation_server.py:93-98 _is_stale_activation returns True only when detected_at <= last_session_finished_at + cooldown. last_session_finished_at is set in a finally AFTER handle_activation returns (line 124-127). The server is single-threaded (listen(1), _serve_once blocks).
Impact: Activations detected WHILE a session is running (the common double-trigger / echo case) are not stale-filtered — they're queued by the socket and processed immediately after the current session ends, because at that point last_session_finished_at is still the previous value and the new detected_at is > it. The guard catches post-session echoes within cooldown but not mid-session re-triggers. Could cause an unwanted second session from TTS audio re-triggering the wake listener.
Fix: Track session-active start time too; treat any activation with detected_at between session_start and session_finished+cooldown as stale.
Test: test_native_wakeword_service case: activation with detected_at during an active session is ignored.

[A3-3] SEV: MEDIUM (no queued/background-delegation result delivery)
Evidence: Search for background/delegate/pending_message/deliver in activation/ returns nothing. answer.py routes heavy work to ask_hermes_turn synchronously (answer.py:36); the turn blocks until Hermes fully completes (hermes_agent_cache.py:113 polling join).
Impact: The desired "Hermes handoffs/background delegation for heavy tasks" is not implemented at the voice layer. A heavy request blocks the entire voice session (and the single-threaded warm server, A3-2) for up to hermes_timeout_seconds = 900s (daemon_config.py:45). No mechanism to say "I'll get back to you" and deliver the result asynchronously. The looping ack (ack_playback.py) just repeats audio for up to 15 minutes.
Fix: Add a background-delegation route: for HEAVY_AGENT requests flagged long-running, dispatch to a background worker / cron-style handoff and free the session, then deliver via TTS or notification when done. At minimum cap the synchronous voice timeout far below 900s and have a "still working" → background transition.
Test: test that a long heavy request transitions to a background/handoff outcome rather than blocking the session past a voice-appropriate threshold.

[A3-4] SEV: LOW (warm-agent interrupt is best-effort; cache cleared on every cancel)
Evidence: hermes_agent_cache.py:119-122 — if the agent doesn't finish after interrupt within _hermes_interrupt_wait_seconds, it logs and clears the cache but the daemon thread keeps running (daemon=True, line 109). hermes_runtime.py warns if no interrupt() method (line 62).
Impact: A cancelled-but-unresponsive agent leaks a background thread and forces a cold re-init on the next turn (cache cleared at line 121/129), reintroducing the startup latency the warm cache exists to avoid. Acceptable as a safety valve but worth a metric.
Fix: Log/count forced-clear events; consider a bounded wait + reuse if the agent does eventually settle.
Test: test asserting cache is cleared and None,True returned when the worker ignores interrupt past the wait window (the path at 119-122).
